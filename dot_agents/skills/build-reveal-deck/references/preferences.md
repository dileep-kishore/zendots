# The user's standing asks for decks

These hold for every deck unless the user says otherwise for one talk. A
request about one deck, such as its slide count or its section names, stays
with that deck and does not belong here.

## How the deck is presented

- The user usually presents by sharing a browser tab and does not read speaker
  notes. Anything the audience must see goes on the slide. Notes are optional
  background only.
- Use a light theme with smooth transitions and animations: a slide
  transition, staggered entrances, and content that builds with clicks where
  that helps the explanation.
- Store decks as SKILL.md step 2 says: in a git project, in its ignored
  artifact folder; in the Presentations folder only when the user asks, in
  that deck's own subfolder. The Presentations folder syncs between
  machines, so keep scratch files and screenshots out of it.

## What a slide looks like

- Pick the layout the content needs:
  - a diagram or mock with a short takeaway;
  - a text slide;
  - a list of several bullets;
  - a table;
  - a comparison.
  
  Use a visual when it explains faster than words, and plain text when it
  does not.
- Keep each slide to one point, with a title that says it. Cut words before
  shrinking the font.
- Diagrams must be accurate. Show the real process, including its branches,
  and add nuance rather than simplify into something wrong.
- Mark mock content as illustrative, and proposals as proposed.
- Prefer a real example with checked numbers over an invented one. Check every
  number against its source, and give the source on the slide.
- Stay at the level the audience needs. Leave out implementation detail the
  room cannot use.
- The summary slide sums up the talk in the talk's own terms. It has no fixed
  structure.

## What the argument needs

- Be concrete. Say what the thing is and how it works, rather than naming a
  vague layer or framework.
- Anticipate the obvious question from this audience, and answer it on a
  slide.
- When the talk is for a meeting with an agenda, make the deck serve the
  agenda's stated objectives.
- Claims about other tools go stale fast. Check them against current primary
  sources before they go on a slide.
- Cut filler. Drop any section or bullet that would read the same in anyone
  else's talk.

## People and branding

- Name no individual people on slides or in notes. Credit the system, team or
  meeting instead. The presenter's name on the title slide is the only
  exception.
- Match the affiliation and branding to the host organisation. For example, a
  KBase talk gets the KBase template and the presenter's KBase affiliation.
- Follow the global writing rules on slides too: no em dashes, plain words,
  one idea per sentence, no bold-label lists.

## How to work

- Back up the deck before a theme overhaul or a large rewrite.
- Inspect the rendered slides yourself after each round of changes, as
  SKILL.md step 4 describes. Reading the code does not catch problems such as
  arrows that appear too early, labels sitting on lines, tiny logos or cramped
  headers.
- Consult the other vendor's model at each stage when the talk matters (for
  example, outline, design and finished screenshots). Fix what it confirms,
  and drop findings it cannot support.
- When the user only asks whether the deck is ready, answer with what is
  verified and what still blocks them. Do not start new edits.
